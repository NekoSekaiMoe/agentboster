# Memoh 与 AgentBoster 全面对比报告

本报告基于对 Memoh（位于 `ref/` 目录的源码快照）与 AgentBoster（仓库主体）两套开源智能体平台的源码级调研，从十六个维度展开横向对比。两套系统都试图回答同一个问题——"如何让一个 AI 智能体长期在线、可托管、可被多渠道触达、并在隔离环境中执行真实任务"，但它们给出了风格迥异的工程答案。Memoh 走的是"每个智能体配一台云电脑"的单体一体化路线，把后端、前端、桌面客户端、容器运行时、可访问性助手打包成一个自洽的 Go 加 Vue 加 Electron 工程；AgentBoster 则走的是"三层松耦合"路线，把权威状态留在 Next.js Web 层，把执行能力下沉到可选的 Linux 守护进程，把终端交互交给瘦客户端 CLI。下面逐项展开。

## 一、自己托管能力、方法与成本

Memoh 的自托管路径高度产品化。官方提供一键安装脚本（`curl -fsSL https://memoh.sh | sh`），该脚本会克隆仓库、根据模板渲染 `config.toml`、提示修改默认口令，然后调用 `docker compose up -d` 拉起整套服务栈。整个生产栈由四个常驻服务（Postgres、migrate、server、web）和若干可选 profile（Qdrant 向量库、Sparse 稀疏检索、webhook-tunnel）组成。值得一提的是 Memoh 支持双数据库后端：PostgreSQL 用于标准部署，SQLite 用于轻量单机部署，通过 `docker-compose.sqlite.yml` 覆盖文件切换，数据落在 `memoh_data` 卷里。这意味着 Memoh 可以在边缘设备上以非常低的成本跑起来——一台能装 Docker 的小机器就够。成本的关键变量是 server 容器以 `privileged: true` 加 `pid: host` 模式运行，因为它内部嵌套了自己的 containerd 实例和 CNI 网络，用来为每个 bot 创建独立的工作区容器；这一点在官方部署文档里被明确标注为安全警告。许可证是 AGPLv3，对二次分发有传染性要求。

AgentBoster 的自托管路径则呈现"双轨制"。一方面，它作为 Next.js 15.5 应用原生面向 Vercel，`package.json` 里直接带 `deploy` 脚本和 `postbuild` 钩子，仓库根目录的 `Dockerfile` 也是完整的多阶段构建（`node:22-alpine` 构建、`tini` 作为 init、非 root 用户运行、内置 healthcheck）。自托管者需要准备 PostgreSQL（必须带 pgvector 扩展，因为记忆和知识库都依赖向量列）和 Upstash Redis 或兼容的 KV 服务；可选地接入 Vercel Blob 做附件存储、Tavily/Brave 做网页搜索。关键差异在于数据库迁移：在 Vercel 生产环境 `postbuild` 会自动跑 `drizzle-kit push` 和 pgvector 确保，但 Docker 自托管必须手动执行 `yarn db:push` 与 `yarn db:ensure-vector`，否则 schema 不会就绪。AgentBoster 采用 MIT 许可证，对商用集成友好得多。

总体而言，Memoh 的"开箱即用度"更高（一条命令拉起完整栈），但代价是强耦合的特权容器和 AGPL 约束；AgentBoster 的部署更模块化、许可证更宽松，但需要自托管者自己组装 Postgres+pgvector+Redis 三件套，并把数据库迁移纳入运维流程。

## 二、安全性

两套系统都在"认证、隔离、工具审批"三个层面下功夫，但实现深度不同。

Memoh 的认证是经典的 JWT（HS256）方案，通过 Echo 中间件实现，支持用户令牌和聊天路由令牌两类，后者专门用于 IM 渠道的入站回复。默认凭据（admin/admin123、postgres/memoh123、固定的 jwt_secret）在所有配置模板里都是明文占位符，文档反复强调必须修改。工具审批系统相当完备：`toolapproval` 包定义了 pending/approved/rejected/expired/cancelled 五种状态和 read/write/exec 三类操作，通过 glob 模式匹配路径与命令，默认等待十分钟超时。访问控制（ACL）是"源感知"的，可以按频道身份、会话类型、线程 ID 粒度配置触发规则。容器隔离层面，每个 bot 拿到名为 `workspace-<botID>` 的独立容器，bridge 二进制和运行时工具包以只读方式挂入，bot 数据写在容器可写快照层。桥接 mTLS 是可选的（strict 模式），但 UDS/本地桥接默认走文件系统信任。最大的安全张力来自 server 容器的特权模式——这是为了嵌套 containerd 不得不付出的代价，文档明确要求"仅在可信环境运行"。

AgentBoster 的安全模型被显式划分为 L0/L1/L2 三层，每层都可以一票否决。L0 是静态正则拒绝规则（Web 端在 `lib/workflow/agent/security/rules.ts`，agentd 端在 `internal/security/l0_rules/`），L1 是基于 LLM 的风险评分（`lib/security/l1-scorer.ts`），L2 是交互式人工授权。自治级别配置决定哪些层会真正触发：`full` 模式下只有硬阻断生效，否则升级规则也会动作。中间件 `middleware.ts` 默认保护所有路由，仅放行登录页、Workflow DevKit 的 `.well-known/workflow/*`、带扩展名的静态资源、IM webhook（用 `AUTH_SECRET` 鉴权），以及带有效 `AGENTD_API_KEY` 的 agentd 回调。会话认证是自研的 HMAC 令牌（非 NextAuth），纯密码学验证不查库，因此可以在 Edge Runtime 上跑；CLI 设备通过配对端点绑定，`jti` 走数据库撤销检查。mTLS 仅在 Web→agentd 方向、且守护进程网络可达时启用，支持证书轮换（API_KEY 支持逗号分隔多值）。L2 审批支持 pass_once/reject_once/pass_until/reject_until，时间窗口授权存在 KV 里带 TTL。

简言之，Memoh 的安全设计更"传统企业"（JWT、ACL、glob 审批），而 AgentBoster 的 L0/L1/L2 三层模型更具"智能体原生"色彩，把 LLM 风险评估显式纳入了安全栈。两者都依赖特权或 root 能力来跑容器，但 AgentBoster 的特权集中在独立的 agentd 守护进程上，Web 层本身可以保持非特权。

## 三、跨平台性

Memoh 在跨平台上投入了大量工程。容器后端有三种：containerd（Linux 默认）、docker、apple（macOS 的 Apple Virtualization 框架，标注为实验性、需 macOS 26+）。配置模板分 `app.docker.toml`、`app.apple.toml`、`app.windows.toml`、`app.kata.docker.toml`，分别对应不同部署形态。桌面客户端通过 electron-builder 打包，明确支持 macOS（DMG、arm64+x64、notarize、最低 macOS 12）、Linux（AppImage+deb+rpm）、Windows（NSIS 安装器）。但有几个硬性 Linux-only 约束：Kata/KVM 路径需要 `/dev/kvm` 直通和宿主侧的 `containerd-shim-kata-v2`；Computer Use 的可访问性助手是 Rust 写的 `a11y-cli`，依赖 `atspi` 0.30 和 zbus，本质上是 Linux AT-SPI2 D-Bus 客户端；bridge 二进制也只构建 Linux 目标，因为它跑在 Linux 工作区容器里。

AgentBoster 的跨平台故事更"分层"。Web 应用（Next.js+Node）天然跨平台，Docker 镜像用 `node:22-alpine`，任何能跑 Node 的地方都能开发。CLI 子包也是跨平台 Node，但要求 `engines.node >=22.19.0`。然而执行平面是硬性 Linux-only：agentd 所有源文件带 `//go:build linux` 标注，启动时需要 root 来设置 cgroups/namespaces，之后降权到配置用户；dbushelper 虽然是纯 Go（CGO_ENABLED=0），但功能上只能跑在 Linux，因为它说的是 AT-SPI2 D-Bus。换句话说，AgentBoster 把"跨平台"限制在了用户交互层（浏览器、终端），把"Linux 强依赖"集中推到了可选的执行后端。

对比来看，Memoh 试图让整个产品（包括桌面 GUI 客户端）覆盖三大桌面 OS，代价是大量平台特例代码和实验性后端；AgentBoster 接受"执行端只能 Linux"的现实，但让用户侧保持平台无关。

## 四、Web UI

Memoh 的 Web UI 是 Vue 3（Composition API、`<script setup>`）加 Vite 8 加 Tailwind CSS 4 的组合，UI 原语来自自研的 `@memohai/ui`（基于 Reka UI 和 class-variance-authority，43 个组件组），状态用 Pinia 3 加 Pinia Colada，表单用 vee-validate 加 Zod，i18n 用 vue-i18n（en+zh）。端口 8082，开发态 18082。镜像构建后用 nginx:alpine 提供静态文件，`MEMOH_SERVER_UPSTREAM` 指向 server。功能页面非常丰富：bot 配置、provider、model、网页搜索、记忆、语音、邮件、Supermarket（技能市场）、用量、人员管理、外观、快捷键、profile、平台、关于、onboarding、登录、OAuth 回调。bot 详情页有概览、设置、桌面（display/runtime）、频道、记忆、MCP、调度、心跳、邮件、容器、网络、工具审批、技能、访问、压缩等十几张 tab。聊天区用 dockview 面板，支持 chat/file/terminal/browser/display 五种面板类型，terminal 用 xterm.js，browser 是 iframe 套工作区 Chrome，display 面板通过 WebRTC 连到工作区的桌面。所有面板用 `renderer: 'always'` 保证切换 tab 时终端/iframe/WebRTC 不丢状态。

AgentBoster 的 Web UI 是 Next.js 15.5（App Router）加 React 19 加 Tailwind 3.4。路由组分 `(auth)`、`(chat)`、`(config)`，外加 `files/`、`memory/`、`schedule/`、`skill/`、`api/`、`.well-known/`。聊天页用 SSR 生成占位 chatId，首条消息时懒创建会话行（避免空会话堆积），布局是 `AdaptiveChatLayout` 加侧栏 cookie 状态，开启了 `experimental_ppr`（Partial Prerendering）。配置 UI 是单一动态路由 `config/[section]`，由 17 个 section 驱动（models、agents、chat、devices、language、knowledge、channels、tts、autonomy、security、tools、mcp、agentd、monitoring、users、audit-logs、raw-json），其中 12 个是 admin-only，普通用户只能碰 chat/devices/language/knowledge/channels。根布局包了 ThemeProvider、I18nProvider、Toaster，全局设了 `noindex,nofollow`。Workflow DevKit 通过 `withWorkflow` 包裹 next.config，步骤代码跑在沙箱 VM 里，`.well-known/workflow/` 路径被中间件放行。

两者都是 SPA 风格的管理控制台，但 Memoh 的 UI 更"重"——一张 bot 详情页就塞了十几张 tab，包含 display/browser/terminal 多面板工作台；AgentBoster 的 UI 更"克制"，把执行能力留给了 agentd 和 CLI，Web 主要承担权威状态、配置和对话。

## 五、CLI 与桌面客户端

Memoh 同时拥有 CLI 和桌面客户端。CLI 是 Go+Cobra，根命令默认启动 Bubble Tea TUI，子命令包括 `chat`（一次性流式聊天）、`bots create/delete`、`start/stop/restart/status/logs`（管理桌面拉起的本地 server 进程，靠 pid 文件协作）、`version`。CLI 自动用本地 admin 凭据登录、令牌存 `cli-token.json`，默认连 `127.0.0.1:18731`。桌面客户端是 Electron 42+electron-vite 4+electron-builder 26，**不**直接 import Web 的 `main.ts`，而是自带 bootstrap 并通过 subpath exports 复用 `@memohai/web` 的页面、布局、store、i18n、设计 token。桌面端的核心是 `src/main/local-server.ts`：它准备本地 SQLite 配置、启动内嵌 Qdrant、解析打包的 `memoh-server`、跑迁移、在 `127.0.0.1:18731` 起 server，写 `local-server.pid.json` 和日志。打包时把 server、cli、runtime、config、providers、qdrant、gstreamer 全塞进 `Contents/Resources/`。CLI 的 PATH 安装是平台特化的（macOS 用 osascript 提权写 `/usr/local/bin/memoh`，Linux 写 `~/.local/bin`，Windows 用 setx 改 HKCU）。在线产品名是 Memoh，离线产品名是 Memoh Local，userData 路径因此不同。

AgentBoster 这边没有桌面客户端（全仓库 grep 不到 electron/tauri/wry）。CLI 存在于 `subpackage/cli/`，是基于 pi 框架的 Yarn Classic monorepo，四个包：ai（类型桩）、agent（会话/循环原语）、agentboster-adapter（存储鉴权、远程模型查找、Web 流、安全评估）、coding-agent（`agentboster` 二进制、TUI、登录、会话、本地工具）。关键是 CLI 是**瘦客户端**——README 明确说"CLI 仅作为瘦客户端负责本地 TUI 与 `local_*` 工具"。所有 LLM 调用、工具编排、会话持久化都在 Web 端发生，CLI 只在本机跑 `local_*` 工具（shell、文件读写）。`agentboster login` 写 `~/.agentboster/config.json`，模式有交互 TUI、`--print` 非交互、`--yolo` 自动批准本地工具（但不会绕过服务端的 L0/L1/L2）。

哲学差异很明显：Memoh 让桌面客户端成为产品的第一公民，自带本地 server 和内嵌向量库，可以完全离线工作；AgentBoster 把"桌面"理解成 agentd 在 LXC 沙箱里控制的 Linux GUI（见第七节），用户侧交互只有浏览器和终端两条路，CLI 永远依赖远程 Web。

## 六、容器支持

Memoh 的容器抽象在 `internal/container/`，三个适配器子包 apple/containerd/docker。每个 bot 的容器创建集中在 `internal/workspace/manager.go`：解析镜像（默认 `memohai/workspace:debian` 或模板 `debian:bookworm-slim`），构造 spec——只读挂入 `/etc/resolv.conf`、`/opt/memoh` 运行时目录、`/run/memoh` socket 目录，可选挂入 bridge mTLS 材料，注入环境变量（UDS socket 路径或 Kata 的 TCP 9090、display 启用时的 RFB 地址和 DISPLAY=:99），命令是 `/opt/memoh/bridge`。容器带标签 `memoh.bot_id`、`memoh.workspace=v3`、资源限额标签，可选 GPU 的 CDI 设备标签。RuntimeRouter 把容器后端和可选的本地工作区组合起来，按容器 ID 前缀或存储驱动路由。基础镜像是标准 debian/alpine/ubuntu，不需要专门的 MCP 镜像——工作区工具包是挂载进去的而非烤进镜像。容器与宿主的通信是 gRPC over UDS。

AgentBoster 有两套独立的容器化层。第一套是 Web 侧的 Vercel Sandbox（`lib/core/sandbox/manager.ts`），用 `@vercel/sandbox` 给每个 Web-UI 会话开一个临时 Linux 容器（Amazon Linux 2023、node24 运行时、allow-all 网络），暴露 `SANDBOX_PUBLIC_PORTS`，做 KV 锁的 get-or-create、超时续期（剩余不足五分钟时续五分钟），并准备好工作区目录树。系统提示词会告诉模型这个容器在会话结束时销毁、有约 40 分钟预算。第二套是 agentd 侧的 docker/docker-strict/lxc 三档（`subpackage/agentd/internal/sandbox/`），文件系统/网络/能力逐档收紧：docker.go 用 Docker socket 配镜像白名单和默认 CPU/内存；lxc_persistent.go 是持久 LXC 工作区，是唯一支持浏览器 profile 和桌面状态跨会话/守护重启存活的档位。隔离模型和 Memoh 不同——AgentBoster 的沙箱是"按会话/按任务"的执行平面，注册到 agentd 节点，而不是"一个智能体一个常驻容器"。agentd 节点本身是单例守护进程（singleton 锁靠 socket+PID+TCP 端口探测），管理多个沙箱，支持多节点调度。

## 七、容器桌面控制

两者都实现了"在容器里跑一个 Linux 桌面并用可访问性树驱动它"，但技术栈和暴露方式不同。

Memoh 的桌面栈在 `internal/display/service.go`（1647 行）。传输是 WebRTC，编码器是 GStreamer，编解码从 SDP 协商（H264 profile-level-id 42e01f、VP8），时钟率 90000、帧率 15，UDP 端口范围可配（默认 30000-30100），首包超时 30 秒、截图超时 15 秒。RFB/Xvnc 在容器内监听 `127.0.0.1:5999`，宿主 display 服务通过桥接的 `DisplayDialContext` 拨入，回退到宿主侧 Unix socket。指针/键盘输入编码为原始 RFB 按钮掩码和 keysym。Computer Use 的快照来自容器内调用的 Rust 助手 `/opt/memoh/toolkit/display/bin/a11y-cli snapshot`，输出 JSON（ref/role/name/center），动作支持 click/type/fill，动作结果带 fallback 坐标——当可访问性够不到目标时回退到原始 RFB 坐标。截图存到工作区路径，从不自动附加到对话，模型必须显式读取。

AgentBoster 的桌面栈在 agentd 的 `internal/agent/desktop/desktop.go`（584 行）加 `desktop_install.sh`。技术栈是 Xvfb（虚拟帧缓冲 `:99`、1280x800x24）+ 会话 D-Bus + AT-SPI2 registry + icewm 窗口管理器 + x11vnc（RFB 端口 5999）+ websockify/noVNC（HTTP 端口 6080）。用户通过 `sandbox.public_port` 工具暴露 6080，然后在浏览器打开 `/vnc.html`——所以是"浏览器可达的 VNC over WebSocket"，不是 WebRTC。工具面有 `desktop_screenshot`（用 `import -window root` 抓帧缓冲返回 PNG，Web 调度器再以 AI SDK image 内容块发给视觉模型）、`desktop_inspect`（返回 AT-SPI2 可访问性树的紧凑文本列表，约 1-3k token）、`desktop_a11y_click`/`desktop_a11y_type`（用可访问性 ref 驱动 GUI 元素，够不到时回退 xdotool）。a11y-helper CLI 是 `subpackage/dbushelper/cmd/a11y-helper/` 里的纯 Go AT-SPI2 D-Bus 客户端，agentd 通过 `sbMgr.Exec` 在沙箱内调用它，stdout 发一个 JSON 对象、诊断只到 stderr，子命令 snapshot/click/type/fill/inspect，引用分层（eN 可交互、xN 仅 inspect），退出码 0/1/2 语义清晰。

差异要点：Memoh 用 WebRTC（更低延迟、更适合浏览器内嵌实时操作），AgentBoster 用 noVNC over WebSocket（实现更简单、依赖更少但延迟特性不同）；两者都用 AT-SPI 做语义化点击而非裸坐标，且都设计了坐标回退；两者的截图都不自动入对话，需模型主动读。

## 八、浏览器自动化

Memoh 的浏览器栈在 `internal/agent/tools/browser.go`（2524 行），CDP 端点硬编码 `127.0.0.1:9222`，桥接在启用 display 时监管一个带界 Chrome/Chromium。工具五个：`browser_action`（导航/点击/输入）、`browser_observe`（带元素 ref 的页面快照）、`browser_remote_session`（把原始 CDP 端点通过隧道 WebSocket 暴露给外部 Playwright/CDP 会话）、`computer_observe`/`computer_action`（桌面级 GUI）。BrowserProvider 只在 display 工作区存在时构造，工具只对非子智能体、启用 display 的会话注册。Usage() 方法把跨工具工作流指引注入提示词，但仅在该 provider 真正注册了工具时——这是"工具用法跟着工具走、永不写进静态提示词"的设计。无头 Playwright 在 Memoh 里只是普通工作区命令，和带界 Browser Use 是两条独立路径。

AgentBoster 的浏览器有两套实现。一是 agentd 的 Playwright 桥（`internal/agent/browser/`）：`browser.go` 管 EnsureBridge/CallBridge/CloseBridge，`bridge.js` 是嵌入式 Node.js HTTP 助手跑在 Unix socket 上，`node_install.sh` 从 TUNA 镜像引导 Node.js 并做 SHA256 校验。首次调用有 30-60 秒冷启动（在沙箱里装 Node+Playwright），之后缓存。浏览器 profile 持久化在 agentd 节点，跨会话和守护重启可用，通过 `browser_save_state`/`browser_load_state`（storageState JSON）和无服务器池互通。二是 `lib/mcp/browser/` 下的无服务器浏览器池（存在但**有意不**通过 `browser_*` 调度器暴露）。Web 侧调度器 `browser.ts` 是薄透传，工具名和 agentd 注册表一一对应，注册了近二十个 `browser_*` 工具（navigate/get_text/get_html/screenshot/evaluate/click/type/inspect/save_state/load_state/list_profiles/close/select_option/hover/upload/tab_*等）。`browser_screenshot` 被特殊处理——守护进程返回 bytes/mime/base64，调度器再以 `{type:'image'}` 内容块重发，让视觉模型真的看到图。浏览器是**带界**真实 Chrome（反检测：真实 UA、`navigator.webdriver` 被屏蔽），跑在持久 LXC 沙箱里。

静态抓取回退在 `lib/mcp/tools/web-fetch.ts`：`web_search` 和 `fetch_url` 内置 MCP 工具做纯 HTTP 抓取加 HTML 剥离，带 JS 渲染检测启发式（检查空 app root、`__next_data__`、webpack、vite 标记），搜索 provider 链是 Brave→Tavily→DuckDuckGo HTML→Bing HTML。

## 十、生产依赖

## 十一、容器控制架构

Memoh 的容器控制契约由 `internal/workspace/bridgepb/bridge.proto`（188 行）定义，ContainerService 服务有 ReadFile/WriteFile/ListDir/Stat/Mkdir/Rename/Exec（双向流）、Tunnel（双向 TunnelFrame：open/data/close）、ReverseHTTP（双向：request/response/error）、ReadRaw（服务端流）、WriteRaw（客户端流）、DeleteFile 等 RPC。传输是 UDS——每个 bot 有宿主侧 socket 目录挂入容器 `/run/memoh`，bridge 监听 `/run/memoh/bridge.sock`，宿主拨 `unix://`；遗留 mcp- 前缀容器和 Kata 容器回退 TCP 9090。Manager（775 行）持有每容器互斥锁 map、gRPC 池（bridge.Pool）、遗留 IP 缓存、hook 服务、bridge TLS 选项，关键方法 EnsureBot/Start/Stop/Delete/WaitForWorkspaceReady（轮询 Stat("/") 最长 45 秒，每 500ms 重试）/MCPClient/DisplayDialContext。Init 时用 `PullImageOptions{Unpack:true}` 准备基础镜像；工作区惰性创建，启动流程处理孤儿快照（删前保数据、建新容器后恢复）、网络重建、UDS 模式下清理遗留 TCP 路由、触发 workspace.start hook。RuntimeRouter 把容器后端和可选本地工作区组合，按容器 ID 前缀或存储驱动路由。

AgentBoster 的容器控制架构是"Web → agentd → 沙箱 → a11y-helper"的多跳链。Web→agentd（可选 mTLS）：节点可达时 `execToolOnAgentd` POST 到守护进程的 `/api/v1/tools/exec` 流端点，客户端配置从 `appConfig.agentd.nodes[0].url` 或 `AGENTD_URL` 取，附 `AGENTD_API_KEY` 和可选 mTLS 证书路径。agentd→Web（始终 HTTPS+API key）：守护进程回调 `/api/agentd/v1/*` 和 `/api/soul/*`，端点涵盖 nodes/register、nodes/heartbeat、l1-score、l2-confirm、tasks、memories、knowledge/search、blob/upload、notifications、agent-config、sandboxes、llm-proxy、sessions/[id]/abort 等数十个；agentd 还通过 `/api/soul`（全局）和 `/api/soul/[sessionId]`（会话覆盖、全局兜底）拉 SOUL 注入自己的系统提示词。agentd→沙箱→a11y-helper：`tools_a11y.go` 的 execA11yHelper 构造 shell 命令，source 桌面 envFile 拿 DISPLAY/DBUS_SESSION_BUS_ADDRESS，再调 `/usr/local/bin/agentd-a11y-helper`，refs 文件 `/tmp/agentd-a11y-refs.json` 是 snapshot/click/type/fill/inspect 间的共享状态。完整浏览器/桌面工具调用链：用户消息进 IM webhook 或 CLI → chatMain 起工作流 → 智能体循环发工具调用 → Web 调度器调 execToolOnAgentd → HTTPS+mTLS 转发到 agentd → gatekeeper 跑 L0/L1/L2 → 批准后执行 → 结果回流并重发为 image/text 内容块。

核心差异：Memoh 是"宿主直连容器内 bridge"的单跳 gRPC/UDS 模型，控制平面和数据平面在同一台机器上紧耦合；AgentBoster 是"Web 权威层、agentd 执行层、可选多节点"的松耦合模型，靠 HTTPS 回调而非共享 schema 协作，执行端可丢弃、可水平扩展。

## 十二、核心架构

Memoh 是"两服务加进程内智能体"模型。Server（Go+Echo，端口 8080）承担 REST API、JWT 认证、数据库、容器管理，**以及进程内运行的 AI 智能体**——没有独立的智能体网关。Web（Vue+Vite，8082）是 nginx 服务的 UI，`/api` 代理到 server。FX（Uber）依赖注入组装 server；智能体通过 `agent.New(deps)` 构造，工具 provider 用 setter 注入打破 DI 环。智能体暴露 Stream()（SSE 事件流）和 Generate()（非流式）加 ExecuteTool()。LLM 集成靠自家 twilight-ai（受 Vercel AI SDK 启发的 Go SDK），client 类型涵盖 openai-completions/responses、anthropic-messages、google-generative-ai、openai-codex、github-copilot、edge-speech。provider 模板有 41 个 YAML 覆盖主流厂商加语音、转录、视频。

AgentBoster 是"三层独立可部署"模型，靠窄 HTTPS 契约通信、无共享 DB schema、无共享代码路径、无共享进程状态。Web（Next.js 15）是权威层：持有会话、模型编排、工具路由、Workflow 运行时、凭据、审计、节点注册表、L2 交互 UI，背靠 Postgres+pgvector+Upstash KV+Workflow DevKit，可部署到 Vercel 或自托管 Docker。agentd（Go）是无状态执行平面：Linux-only 守护进程，向 Web 注册、每 30 秒心跳、跑沙箱工具调用（docker/docker-strict/lxc）、执行宿主侧 L0/L1/L2、维护本地缓存和指标，支持多节点（`selectBestNode` 调度）。CLI 是瘦终端客户端：无模型推理、无会话持久化，本地会话文件只是 Web 数据的临时镜像，`--resume` 从远程拉消息。dbushelper 是纯 Go AT-SPI2 库加 a11y-helper CLI，被 agentd 的 tools_a11y.go 消费，不被 Web 或 CLI 直接寻址。Web 是唯一真相源——README 说"执行端可丢弃"，agentd 节点和 CLI 进程可伸缩重启而不影响会话连续性。强异步模型：所有 LLM 调用、工具循环、子智能体编排落地为可恢复的 Workflow DevKit 步骤（`persistStepDeltaAndUsageStep` 把增量写进 messages 表），任何执行端死掉，工作流暂停并在下一次 route-message 或 agentd 回调时从中断点恢复。

## 十三、MCP 与内置工具/指令

Memoh 的 MCP 在 `internal/mcp/`（18 文件）：ConnectionService 和 OAuthService 管每 bot 的 MCP 连接，tool_gateway_service 把 MCP 工具暴露给智能体，http_tools 处理 HTTP 传输的 MCP server，result_limit 截断大结果。`cmd/mcp/` 是 stdio MCP 传输二进制。Federation 工具（`tools/federation.go`）把 mcp.ToolSource 适配成 ToolProvider，过滤内置工具名冲突、跳过子智能体会话，跨工具指引仅在至少一个 MCP 工具注册时注入。内置工具库（`internal/agent/tools/`，49 项）覆盖：文件系统/容器（read/write/list/edit/apply_patch/exec）、后台任务（list/get/kill/wait/wait_until）、消息（send/react/speak/get_contacts/list_sessions/get_messages/search_messages）、记忆（search_memory）、技能/子智能体（list_skills/use_skill/spawn_agent/send_message/list_agents）、调度（list/get/create/update/delete_schedule）、浏览器/计算机（browser_action/observe、computer_observe/action、browser_remote_session）、网页（web_search/web_fetch）、媒体生成（generate_image/video、transcribe_audio）、用户交互（ask_user）、邮件（list_email_accounts/send/list/read）。斜杠命令系统在 `internal/command/`（45 文件），处理器含 compact/context/email/heartbeat/language/mcp/memory/menu/model/reasoning/schedule/search/settings/skill/status/usage 等，全部 i18n 本地化。

AgentBoster 的 MCP 既支持客户端也提供内置 server。客户端用 `@ai-sdk/mcp` 的 createMCPClient（动态导入），支持多种传输。内置 MCP server（`lib/mcp/builtin/`）四个进程内 server 通过 InMemoryBuiltinMcpTransport 暴露，实现 JSON-RPC（initialize/tools/list/tools/call，协议版本 2025-11-25）：web（web_search/fetch_url）、firecrawl（firecrawl_scrape 给渲染重的页面）、github（仓库检查、issue、PR）、context7（项目文档/代码库指引）。守护桥 `executeBuiltinMcpTool` 让 agentd 通过 `/api/agentd/v1/tools/mcp-exec` 调内置 MCP 工具，绕过绑定到 Workflow 'use step' 的 AI SDK ToolSet。Web 侧内置工具 BUILT_IN_TOOLS 含 sandbox/browser/desktop/memory/localSkill/schedule/taskSummary/subAgent/agentdNodes/localCli/askQuestion/sequentialThinking。createResilientToolSet 用 Proxy 包裹合并工具集，给幻觉/拼写错误的工具名合成回退（别名解析→编辑距离≤2→结构化错误）而不污染模型可见列表。Plan 模式过滤为只读工具白名单。agentd 侧工具（tools_*.go）含 exec/file/git/codeact/browser_v2/desktop+a11y/web+web_rendered/media/memory/knowledge/skills/subagent/task_summary/vault/deliver/misc/mcp/sandbox_destroy/question，外加 agents_md.go（AGENTS.md 解析转发）。斜杠命令 IM 侧有 /start/new/session/stop/cancel/retry/model/approve/reject/compact/help/memory。Chat SDK 用 `chat` 4.29.0 加每平台适配器（discord/gchat/slack/teams/telegram 均 4.29.0，加 state-redis）。

## 十四、内置提示词

Memoh 的提示词模板在 `internal/agent/prompts/`，10 个 markdown 文件：system_common.md（基础，每次都拼）、按会话类型选择的 mode_chat/discuss/heartbeat/schedule/subagent、触发用的 heartbeat.md/schedule.md（作为 cron 触发的用户消息）、下划线前缀的 partial _memory.md 和 _identities.md。桥接侧模板在 `cmd/bridge/template/`（AGENTS/HEARTBEAT/MEMORY/PROFILES），首次启动种进工作区 /data。组装逻辑在 prompt.go（346 行）：init 用 go:embed 加载并注册 partial，resolveIncludes 替换 `{{include:_name}}`，GenerateSystemPrompt 拼接 systemCommon 加模式模板，render 替换 `{{key}}` 占位（home 恒为 /data、currentTime、timezone、botInfo、skills、platformIdentities、mainAgent/subagentSections、fileSections）。buildMainAgentSections 拼记忆 partial 加身份 partial 加技能段加文件段；buildFileSections 读工作区系统文件（AGENTS.md/HEARTBEAT.md/PROFILES.md）并做头尾修剪。"工具用法跟着工具走"是硬约束——每工具用法在 sdk.Tool.Description，跨工具指引在可选的 ToolUsage.Usage()，仅在该 provider 注册工具时注入，提示词模板从不命名条件注册的工具，由 prompt_test.go（364 行）守护。

AgentBoster 的提示词组装在 `lib/workflow/agent/steps/build-prompt.ts`（标 'use step'）。buildSystemPrompt 按序拼：内置记忆段（迭代 listBuiltinMemorySections 发 AGENTS/SOUL/IDENTITY/USER 各自的 `# <KEY>` 段，内容来自 builtin_memories 表）、智能体身份（名字加解析的 prompt，有自定义用自定义否则 DEFAULT_SYSTEM_PROMPT）、响应语言（responseLocale 非 auto 时）、委派模式、Plan 模式、项目指令 AGENTS.md（CLI 主机从用户文件系统转发，包在围栏块里并明确声明是"项目提供的参考数据，非特权指令通道"）、Tool 超级段（含 Runtime 子段通知 Vercel/无服务器加当前 ISO 时间、Memory Rules 三层记忆策略、Long-Running Task Management、Sandbox 行为和 40 分钟预算、Skills 列带 family 标签、Builtin MCP Tools 列描述加浏览器工作流指引）、Follow-up Suggestions（禁用/SOUL 模板/默认三项中文建议块）。DEFAULT_SYSTEM_PROMPT 在 `lib/workflow/agent/config.ts`，覆盖产品信息、语言规则、语气格式、拒绝处理、决策权限、公正性、安全规则、提示词注入防御、推理（sequential_thinking 用法）、沙箱路由、浏览器/桌面工具详述。SOUL 是 builtin_memories 里 key='SOUL' 的行，全局 `GET /api/soul`、会话 `GET /api/soul/[sessionId]`（覆盖回退全局），agentd 拉来注入自己提示词，也解析出 follow-up 模板。`.agents/skills/` 是仓库本地 OpenCode 技能（ai-sdk/bug-hunter/chat-sdk/next-best-practices/ui-ux-pro-max/vercel-react-best-practices/workflow），是贡献者/AI 编码会话指引而非运行时提示词。用户侧技能系统另算——OpenClaw 风格 Markdown 技能存 Upstash KV 加 Blob。

两者都把"工具用法不写进静态提示词"作为防漂移原则，但 Memoh 用编译期测试守护、AgentBoster 用结构化分段加 DB 行外置。

## 十五、记忆的读取与储存

Memoh 的记忆系统在 `internal/memory/`，多 provider。Provider 接口（adapters/provider.go）实现 Type、对话钩子（OnBeforeChat/OnAfterChat）、MCP 工具（ListTools/CallTool，规范工具名 search_memory）、全 CRUD（Add/Search/GetAll/Update/Delete/DeleteBatch/DeleteAll/Compact/Usage），可选能力 SourceSyncProvider（Status/Rebuild，从权威源重建派生存储）和 SemanticCompactProvider（LLM 合并加源归档加重建）。Registry 缓存 provider 实例按 DB id 键控，懒实例化。实现：builtin/（15 文件，集成 Memoh 记忆，分 dense_runtime 稠密向量、sparse_runtime BM25 稀疏、file_runtime 文件扫描三种检索策略，compact.go 语义压缩，context_packer.go 上下文打包）、qdrant/（向量客户端）、sparse/（BM25 客户端，连 8085 的 memohai/sparse 服务）、memllm/（LLM 抽取）。外部 provider：mem0/（Mem0 SaaS）、openviking/（OpenViking SaaS），无需 Compose profile，在 admin UI 配 base_url 加 key。LLM 抽取用 _memory.md partial 加 formation/compact 代码路径。记忆按 bot 作用域键控——一个 bot 绑多个频道（Telegram/Discord/Web）共享一个记忆库；bot OwnerUserID 加 channel_identities 加 user_channel_bindings 跨平台统一入站身份。memory_providers 表存适配器配置，bot_settings.memory_provider_id 按 bot 选 provider。

AgentBoster 的记忆是三层架构背靠 Drizzle+Postgres+pgvector。Schema：builtin_memories（按 AGENTS/SOUL/IDENTITY/USER 键控的纯文本，注入每次系统提示）、session_memories（每会话摘要，带 summaryVersion 和 isCurrent 标志）、long_term_memories（跨会话事实，memoryType 枚举 fact/preference/decision/conversation，importance 1-10，可选 key 做去重/抽取 upsert，唯一在 (userId,key)）、long_term_memory_chunks（分块嵌入：embedding 变维 pgvector、embeddingModel、embeddingDimensions、tsv tsvector 关键词、lastAccessedAt）。召回管线：recall.ts 的 recallRelevantMemories 每轮自动注入 top-K（默认 5）长期记忆，min confidence 0.02，用关键词候选（限 10）加近因/重要性回退（限 20），由 scoreMemoryRelevance（LLM 的 L1 评分器）打分；search.ts 是混合搜索——向量加关键词候选用 Reciprocal Rank Fusion（RRF k=60）合并，归一化到 0-1，带记忆衰减（DEFAULT_DECAY_RATE=0.05，重要性抵抗衰减）；cross-reranker.ts 可选交叉重排（池乘子 4×topK）；extract.ts 抽取写新长期记忆。知识库是独立 RAG 系统（knowledge_bases 团队/私有可见性、knowledge_documents 文本/文件/url/import 源、knowledge_connectors url/mem0/http 同步状态、knowledge_chunks 嵌入加 tsvector）。

两者都支持向量加关键词混合检索和 LLM 抽取，但 Memoh 把 provider 抽象做得很彻底（可外接 Mem0/OpenViking），AgentBoster 则把记忆、会话摘要、知识库三个概念分库分表，pgvector 内嵌、无外部向量服务依赖。

## 十六、IM 集成、本地化与模型技能

Memoh 的频道适配器在 `internal/channel/adapters/`，14 个平台子包：dingtalk、discord、feishu、line、local、matrix、misskey、qq、slack、telegram、wechatoa、wecom、weixin。知名 ChannelType 常量 12 个，misskey 动态注册。频道基础设施庞大：adapter/manager/registry（线程安全，必须 NewRegistry 创建显式传递）、directory（ChannelDirectoryAdapter 联系人/群组查找 ListPeers/Groups/GroupMembers/ResolveEntry）、inbound 出站管线、webhook 端点和处理器、toolcall 格式化/过滤/摘要（内联展示）、error_redaction、public_host、capabilities、schema。i18n 在 `internal/i18n/`，零依赖本地化目录，内嵌 JSON（en/zh/ja 三语），扁平化点键，查找回退请求语言→英语→键本身；这一层只本地化命令 UI，与 bot 聊天回复语言（settings.Language）和 IM 平台用户语言无关。技能在 `internal/skills/skills.go`（642 行），技能是命名子目录里的 SKILL.md，从多根发现（/data/skills 管理态、/data/.skills 遗留、/data/.memoh/skills 索引、/data/.memoh/plugins 插件、外部注入根），源类型 managed/legacy/compat/plugin，状态 effective/shadowed/disabled，动作 adopt/disable/enable，索引文件 /data/.memoh/skills/index.json 跟踪覆盖和内容哈希；技能通过 list_skills/use_skill 工具和系统提示的 skillsSection 暴露。Supermarket 页消费 plugins/skills API 从 supermarket.memoh.ai 安装策展模板。ACP 托管外部 Claude Code 和 Codex：acpagent/session_pool.go（1680 行）单服务器实例内存运行时池，rt_<uuid> OS 进程，绑定的 30 分钟空闲回收、未绑定 5 分钟、每 bot 最多 4 个未绑定，状态 starting/idle/active/closed。

AgentBoster 的 IM 集成通过 `@chat-adapter/*` 家族加额外项：telegram、discord（next.config 把 @chat-adapter/discord、@discordjs/ws、discord-interactions、discord.js 列为 serverExternalPackages 防止打包破坏）、slack、teams、gchat，飞书用 @larksuiteoapi/node-sdk（事件适配器加密键加验证 token，在 lib/bot/adaptor.ts 的 ExtraAdapters 单独配），QQ 用 qq-official-bot（webhook 适配器带端口/路径）。适配器工厂 createBotAdapters 动态导入——仅该频道 enabled 时才加载。统一通知 getNotificationManager 把 L2 决策、任务完成等派发到用户偏好频道。本地化在 `lib/i18n/`，七语：en-US/en-GB/zh-CN/zh-TW/zh-HK/ja/ko，I18nProvider 包根布局，配置 UI 有 language 段，BotLocale 类型和 localeLabels 驱动响应语言系统提示段，默认系统提示的语言规则让模型镜像用户语言。模型技能 `.agents/skills/` 七个 OpenCode 技能（贡献者/AI 编码会话用，非用户面）。用户面技能系统是 OpenClaw 风格 Markdown 技能存 Upstash KV 加 Blob，有 listSkillMetas/getSkillDetail/upsertSkillDetail/persistManualSkill/syncRepoSkillDetails 和从 git/ClawHub 同步，技能有 entrypoint 路径，localSkillTool 暴露 list/get/getSkillFile 加写/更新/删除。AI SDK 用 `ai` ^6.0.197 核心，@ai-sdk/anthropic/google/openai/openai-compatible/react/mcp 提供 provider，lib/ai/providers.ts 的 getProvider 按 format 切换并应用可选 preset，模型目录在 Web 解析后通过 /api/cli/models 推给 CLI/IM。

## 总结性观察

把十六个维度合起来看，两套系统的产品定位其实指向不同的优先级。Memoh 的优先级是"把整个云电脑体验打包成一个能一键起的产品"——所以它在桌面客户端、WebRTC 桌面流、多 IM 频道、Kata 强隔离、Supermarket 技能市场、ACP 托管外部编码智能体上投入巨大，代价是一个 privileged 的 server 容器、AGPL 许可证、以及一个相当重的单仓库（Go+Vue+Electron+Rust 四种工具链）。它的"每个 bot 一台电脑"隐喻非常完整，从文件系统到桌面到浏览器到记忆都隔离，并且桌面客户端可以完全离线自带 server 和 Qdrant。

AgentBoster 的优先级是"权威状态集中、执行能力下沉、交互终端多样"——所以它把 Next.js Web 做成唯一真相源，把 agentd 设计成可丢弃、可多节点水平扩展的 Linux 执行平面，把 CLI 设计成只跑本地工具的瘦客户端，把安全显式分成 L0/L1/L2 三层并把 LLM 风险评分纳入安全栈。它的容器是按会话/按任务的临时执行平面而非按 bot 的常驻隔离，桌面控制走 noVNC over WebSocket 而非 WebRTC，记忆用 pgvector 内嵌而非外部向量服务。代价是自托管者要自己组装 Postgres+pgvector+Redis 三件套并手动跑迁移，且没有原生桌面客户端。

对选型者而言：若需要的是"给每个团队成员或家庭成员配一个常驻在线、有自己电脑和记忆、能被十几个 IM 触达的智能体"，Memoh 的完整度更高；若需要的是"一个可扩展、可在 Vercel 上跑、执行端可丢弃可换 Linux 节点、安全分层可审计的智能体平台"，AgentBoster 的架构更现代更松耦合。两者在浏览器自动化、容器桌面控制、AT-SPI 可访问性驱动这些具体能力上殊途同归，差异主要在工程组织和部署形态而非能力有无。
